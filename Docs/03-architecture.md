# معماری پیشنهادی

## تصمیمات اولیه

C# و WPF روی .NET 10 LTS برای دسکتاپ ویندوز پیشنهاد می‌شود: پردازش تصویر داخلی WPF، بلوغ پشتیبانی RTL و تفکیک MVVM مناسب است. این انتخاب هنوز تأیید نهایی نشده؛ WPF در Windows محدود است، و طراحی بصری نیازمند استایل اختصاصی است. مایکروسافت برای برنامه‌های عمومی جدید WinUI 3 را نیز توصیه می‌کند؛ پیش از تثبیت، یک نمونه کوچک از RTL، عملکرد نمایش شبکه و دسترس‌پذیری مقایسه شود. [.NET 10](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-10/overview)، [Microsoft Windows developer FAQ](https://learn.microsoft.com/en-us/windows/apps/get-started/windows-developer-faq)، [WPF imaging](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/graphics-multimedia/imaging-overview).

## اجزا و وابستگی

```text
WPF UI (Views / ViewModels)
        ↓ درخواست‌ها و نتیجه‌های مستقل از UI
Application (workflow, validation, reporting)
        ↓
Domain (lift map, zones, profile, transforms, losses)
        ↑ پیاده‌سازی interface
Infrastructure (BMP/TIFF, filesystem, report)
Format adapters (هر کنترلر/گونه به طور مستقل)
```

دامنه به UI، مسیر فایل و نوع WPF وابسته نیست. کدک‌های تصویر و ماشین با قرارداد جداگانه و تزریق وابستگی ثبت می‌شوند. افزونه شخص ثالث در MVP لازم نیست؛ جداسازی adapter به معنی اجازه اجرای کد ناشناس نیست.

## مدل معنایی پیشنهادی

- `LiftMap`: عرض = تعداد ستون قلاب منطقی، ارتفاع = پود؛ `cell[pick, hook]` مقدار منطقی `Raised`/`Lowered`، مستقل از اینکه سیاه یا سفید در تصویر کدام است. مبدأ داخلی: قلاب منطقی صفر از چپ پیش‌نمایش، پود صفر از بالای پیش‌نمایش؛ این قرارداد نمایش است و جهت فیزیکی را تعیین نمی‌کند. در UI شماره‌گذاری از ۱ نمایش داده شود.
- `Zone`: شناسه، نوع، بازه یا نگاشت صریح قلاب‌ها، محتوا/پود و جهت. هر نوع منطقه پشتیبانی‌نشده یا متادیتای نامعلوم باید مسدود یا به صراحت در گزارش درج شود؛ هرگز خودسرانه ادغام نشود.
- `MachineProfile`: شناسه و نسخه، سازنده، مدل، کنترلر و firmware در صورت شناخت، ظرفیت و قلاب فعال، نقشه منطقی→فیزیکی، مبدا/جهت، مناطق، محدودیت نام/رسانه و پارامترهای شناخته‌شده. نگاشت باید دامنه، برخورد و فاصله‌ها را اعتبارسنجی کند و فقط با قواعد مجاز پروفایل non-bijective باشد.
- `DesignDocument`: محتوا، مناطق، گزینه‌های تفسیر تصویر، منشأ و متادیتای شناخته‌شده؛ اگر داده‌ای ناشناخته باشد، وضعیت آن صریحاً `unknown` باشد، نه مقدار پیش‌فرض ساختگی.
- `ConversionReport`: هش ورودی/خروجی، نسخه ابزار و کدک، پروفایل و تنظیمات، ابعاد و مناطق، عملیات، خطاها، هشدارها و اتلاف. هش جهت شناسایی است نه اثبات ایمنی.

ذخیره ماتریس با بیت‌پک یا پردازش قطعه‌ای در backend بررسی شود؛ دسترسی تصادفی و اندازه‌ها باید با عدد صحیح بررسی‌شده محافظت شود. نمایش مجازی، tile و cancellation برای نقشه بزرگ؛ جزئیات عملکرد به بنچمارک وابسته است.

## قرارداد مفهومی کدک

- `Probe(stream, profile)` تنها شواهد و احتمال نوع را بازمی‌گرداند، نه تأیید قطعی از روی پسوند. ورودی ناشناخته رد شود.
- `Read(stream, profile, limits) → document + diagnostics` و `Write(document, stream, profile, options) → diagnostics` باید قطعی و قابل لغو باشند. وابستگی به UI و نوشتن بر فایل ورودی ممنوع.
- `Capabilities` به تفکیک گونه، نسخه کنترلر، خواندن/نوشتن، چندمنطقه، اطلاعات قابل حفظ و وضعیت آزمون. فقط حالت‌های اثبات‌شده در UI فعال‌اند.
- هیچ اطلاعات ناشناخته‌ای بی‌صدا کنار گذاشته نشود. کدک موظف است خطا یا هشدار اتلاف همراه با امکان جلوگیری از صدور برگرداند.
- فایل موقت کنار مقصد تولید و پس از اعتبارسنجی با عملیات جایگزینی مناسب سیستم فایل نصب شود؛ شکست یا لغو نباید خروجی جزئی را موفق جلوه دهد. در مقصدهای غیرمحلی، خاصیت اتمی تضمین نمی‌شود و باید خطا/محدودیت نمایش یابد.

## حریم خصوصی و استقرار

پیش‌فرض آفلاین؛ بدون telemetry یا انتقال طرح. تنظیمات و گزارش محلی در مسیر کاربر با امکان حذف و بدون ثبت خودکار محتوای طرح. وابستگی‌ها از منابع معتبر و نسخه ثابت، با بازبینی مجوز و آسیب‌پذیری؛ پشتیبانی نصب، بروزرسانی و rollback قبل از انتشار مشخص و آزمایش شود. آزمون ساخت و رابط ویندوزی روی runner ویندوز لازم است؛ آزمایش صرفاً لینوکس برای WPF کافی نیست.
